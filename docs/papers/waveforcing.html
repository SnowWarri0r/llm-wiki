Wave Forcing
砍一条边，换一条流水线

DENG Lab MLSys Team · Shanghai Jiao Tong University · 项目博客（2026，arXiv 未出）

它要让长视频一边生成、一边解码，而且在稳态时每隔约 95 毫秒就交出下一块画面。难点不是“多放几张卡”，而是前后视频块在每层注意力里互相依赖，卡与卡不得不反复碰头。Wave Forcing 从依赖关系本身下手：删掉不必要的反向边，再让 runtime 沿着剩下的单向依赖跑流水线。

先记这一句造成逐层同步的不是混合噪声窗口本身，而是「噪块影响净块」那条反向注意力边。删掉它，执行图从环变成 DAG：扩散侧的完整 DiT 副本各守一个去噪阶段，较净阶段逐层把 KV 发给较噪阶段；后面再接独立的 VAE 解码流水线。作者在 8×H200 上报告 117.7 E2E FPS：生成约 100 秒视频需要 13.56 秒。不过这仍是项目博客与开源推理系统的结果，论文和训练代码尚未公开。

§ 01三代流式方案：各拿半张好牌

块优先（CausVid / Self-Forcing 系）

一块做完才下一块

chunk c 的全部去噪步结束才开始 c+1——请求内部是串行链，多卡吃不满。

Rolling Forcing

活窗口，环形执行

混合噪声窗02里几个 chunk 同时推进（越早越干净），每步吐最净那块。上下文是活的；代价是窗内注意力双向——每层 Transformer 都要全窗同步，Ulysses/Ring 也逃不掉逐层全局协调。

Live Avatar

干净流水，冻结历史

一卡一阶段的反对角流水、只传 latent；但每阶段的历史 KV 冻在固定噪声态，不被后面更干净的表示刷新——建模上的让步。

Wave Forcing 各拿两家的好牌：Rolling Forcing 的活上下文 + Live Avatar 的硬件流水。钥匙是下面这条边。

§ 02先把整机拼起来：一块视频从噪声走到画面

先只认数据流，不急着记通信名词。输入是文本和一长串随机 latent；扩散组逐块去噪，store rank 把已经干净的历史整理成可复用 KV；CPU 队列把完成的 latent 块交给另一组 GPU；VAE 组只持有各自那一段解码器，最后吐出像素帧。

拿 4+3 的长视频实验走一遍：399 个 latent 帧先切成 133 块，每块 3 帧。扩散组共有 5 个进程：4 个去噪阶段加 1 个 store；VAE 组另有 3 个进程，所以一共 8 张卡。流水线灌满后，每个 tick 完成一块，VAE 的 4× 时间放大把 3 个 latent 帧变成 12 个像素帧。

N_{\text{chunk}}=399\div3=133,\qquad N_{\text{tick}}=133+5-1=137

第二条式子里的 5 是扩散组的进程数，不是去噪步数；多出来的 1 就是 store。前面的 +5-1 是流水线灌入和排空的固定开销。后文先讲为什么依赖图能变成单向，再讲这 137 个 tick 怎么斜着跑。

§ 03关键观察：窗口无罪，反向边有罪

砍掉反向边之后：噪块照旧看到所有更净的前辈，净块不再回头。于是“谁必须等谁”有了固定方向，不同 chunk 才能落在不同 GPU 上错步执行。代价是旧权重并没学过这张 mask：§ 07 的对照显示，直接把 Rolling Forcing 权重切成块因果推理，长视频质量漂移08从 0.618 升到 2.825；重新蒸馏后才降到 0.030。

§ 04Wave Parallelism：chunk 像波一样斜着流

现在把 § 03 的单向依赖放到硬件上。4 个去噪 rank 和 1 个 store rank 各自加载完整 DiT；3 个 VAE rank 只加载解码器的连续分段。chunk 每个 tick 向下一阶段移动一格，在 GPU×时间矩阵里就形成一条斜波。

读图要点盯住一种颜色沿对角线走：它在 r0 做第 1 步去噪（最噪、要看全部前辈的 KV），下一 tick 到 r1 做第 2 步……第 4 步做完变干净，KV 进存档位，再流过三段 VAE 出帧。稳态时 8 张卡全满，每 tick 吐一块 = 12 帧画面（chunk = 3 个 latent 帧 × VAE 时间 4×）。
KV 单向发布04每层 Transformer 算完，较净的 rank 把这一层的 K/V 发给更噪的消费者。4-step 默认时间表是 [1000, 750, 500, 250]；公开 Preview 是另一套 5-step [1000, 800, 600, 400, 200]，两者不能混写。
阶段之间为什么还要“重加噪”每个 rank 先预测一份较干净的 x_0；下一个 rank 却期待自己噪声等级上的输入，所以 runtime 调用 scheduler 的 add_noise 把它送回下一档噪声。种子固定为 1000 × chunk编号 + stage编号，同一块跨进程仍能复现。
“没有 collective”要加限定优化掉的是每一层 KV 的全组 all-gather。当前 commit 在 tick 边界搬 latent 仍调用一次 world all_gather，第一个 clean anchor 也会广播。它减少的是几十层里反复出现的同步墙，不是把所有集合通信都删光。

§ 05慢 rank 不是瓶颈，是藏通信的口袋

块因果给了一个白捡的礼物：各 rank 的每层计算量天然不等。最噪的 r0 上下文最长（约 8 块，要看全部前辈），每层算得最慢；越净的 rank 上下文越短（约 5 块）、算得越快。快的先发 KV、慢的还在算——通信恰好塞进关键 rank 的计算窗里。14B 实测：r0 每层 646ms，其余 575–581ms，约 70ms 顺风差。

传输本身再拆三种税

字节税

FP8 KV

BF16 每个值 2 字节，FP8 每个值 1 字节，所以同样数量的 KV 理论字节先减半；项目微测的通信约 79→40ms。可量化、还原也要时间，配 SageAttention07 时净收益反而不稳。当前 paged 模式也明确不支持 one-sided FP8，不能把所有优化画成一条必然叠加的直线。

协调税

copy engine 单边写05

生产者用 cuMemcpyPeerAsync 直写消费者的 IPC 显存，设备端 generation flag 替代 NCCL 配对收发——不占 SM，微基准 343 GB/s。

组装税

paged 直写06

生产者写进消费者注意力缓冲的固定槽位，注意力就地读前缀——免每层 torch.cat（18.49→4.08ms）。推荐组合 = causal + paged。

§ 06VAE：跨卡重叠，且按实测时间切

扩散提速到极限后，解码成了尾巴。同一张卡上并发解两块视频听着并行，实则抢同一批 SM、两个都变慢；正解是解码器也切成 3 段各占一卡，连续 chunk 在卡间错开。切分点有讲究：480×832 下高分辨率上采样块是 memory-bound，同 FLOPs 的块壁钟能差 6×——按 FLOPs 均分必然一段过载。

代码里的目标可以写成下面这句：VAE 的解码单元顺序不能打乱，只能挑两个切点，把连续单元分成三段；在所有合法切法中，让“最慢那一段”的实测时间尽量小。

\min_{0=c_0<c_1<c_2<c_3=L}\;\max_{j\in\{0,1,2\}}\;\sum_{i=c_j}^{c_{j+1}-1} t_i

L 是解码单元总数；t_i 是第 i 个单元实测多少毫秒；c_1,c_2 是待选择的两个切点；外层 \min 表示遍历切法，内层 \max 只盯最慢 stage。举个手算例：6 个单元实测为 [12,10,45,14,15,13] ms。按单元数二等分会切成 [12+10] / [45+14] / [15+13]，三段是 22 / 59 / 28 ms，流水线每轮得等 59ms；改切成 [12+10] / [45] / [14+15+13]，变成 22 / 45 / 42 ms，最慢段从 59 降到 45ms。仓库用动态规划把真实几十个单元做同一件事。

5+2 拓扑为什么有 85 FPS 的天花板preview checkpoint 用 5 去噪 + 2 VAE：扩散侧能跑过 120 FPS，但两段 VAE 每段太厚，最长段拖过下一块到达时刻——相邻 chunk 被迫在同两张 VAE 卡上抢 SM，双双变慢。4+3 的三段时间均衡 VAE（95/99/96ms）跟上 DiT 的 ~95ms 节奏，只剩 ~3.5ms 残余壁垒。

§ 07数字与质量：先把三种 FPS 分账

先看两条真正用到的公式，避免把稳态吞吐和整条链路混成一个数。每个稳态 tick 交出 12 个像素帧；最佳 Sage+paged 配置的 tick p50 是 95.4ms，所以稳态 FPS 是：

\mathrm{FPS}_{\text{steady}}=\frac{12\ \text{frames}}{95.4\ \text{ms}\div1000}=125.79\approx125.7

整条链路还要付灌入、排空和 VAE 尾巴。完整 1596 帧用了约 13.56 秒，因此：

\mathrm{FPS}_{\text{E2E}}=\frac{1596\ \text{frames}}{13.56\ \text{s}}=117.70

这也解释了为什么 126.5 的“最快稳态 FPS”不是最终赢家：那一行用了 Sage+W8A8，DiT 与 VAE 的完整时钟算下来只有 115.9 E2E FPS；不带 W8A8 的 Sage+paged 最后反而是 117.7。

§ 08代码能确认什么，仍然缺什么

最后把“博客主张”“当前实现”和“尚未公开”分开。这样等论文出来时，哪些地方需要重写一眼就能看见。

代码可确认

波前调度不是概念图

engine.py 里确实用 c=t-r 决定本 rank 当前处理哪一块，其中 r 是 rank 编号；总 tick 数写成 N_{\mathrm{block}}+N_{\mathrm{rank}}-1。每个阶段只在自己的对角线上工作。

代码可确认

长历史不是无限 KV

runtime 最多保留 8 个 clean page：第一个锚点加最近 7 个；真正送进注意力的 working set 还受最大窗口限制。所谓“无限生成”是输出长度可持续推进，不是每次注意力都回看从第 1 帧到现在的全部历史。

实现边界

逐层 KV 去 collective，不等于全系统零 collective

paged / one-sided 路径把 KV 直写远端槽位；但 tick 边界的 latent migration 仍是 world all_gather，初始化 clean anchor 也有 broadcast。博客的“no global collective barrier”应限定为关键的逐层 KV 路径。

尚未公开

训练过程仍是黑箱

没有教师模型、rollout 长度、蒸馏 loss、数据规模、优化器和训练成本；也没有 4-step 正式 checkpoint。现阶段能复现的是推理 runtime 与公开 5-step Preview，不是完整训练闭环。

我的判断这是信息量很高的系统 release，但还不是一篇可逐项复现的论文。最扎实的部分是 WaveRT 的通信、buffer 与 VAE 流水；最关键、同时最缺证据的部分是 rollout-aligned 蒸馏。arXiv 出来后，优先补训练目标、teacher/student rollout 对齐方式、block-causal mask 的正式定义和消融。

附录词汇表

  1. Rolling Forcing — 流式视频生成方法：维护一个混合噪声滑窗，窗内多个 chunk 一次联合前向共同推进，每步吐出最干净的一块。Wave Forcing 的算法基座。
  2. 混合噪声窗（mixed-noise frontier） — 同一时刻窗内各 chunk 处于不同去噪进度（越早越干净）的滑动窗口；好处是后面的噪块始终能看到前面「越来越干净」的活上下文。
  3. 块因果注意力（block-causal） — chunk 内部全注意力、chunk 之间只允许「噪看净」的单向注意力；Wave Forcing 对 Rolling Forcing 的唯一算法修改。
  4. KV 发布 — 每层 Transformer 算完后，把该层的 Key/Value 状态发给下游消费者；块因果保证发布方向固定，因此不用让所有 rank 在每一层都做全组 collective。tick 边界搬 latent 仍有一次 all_gather。
  5. copy engine 单边写 — 用 GPU 的拷贝引擎（cuMemcpyPeerAsync）直写远端 IPC 显存，配设备端 generation flag 判定数据就绪；不占计算 SM、免 NCCL 配对收发。
  6. paged 直写 — 生产者把 KV 直接写进消费者注意力缓冲中的固定页槽，消费者就地读前缀、免每层重新拼接（torch.cat 18.49→4.08ms）。
  7. SageAttention / W8A8 — 两档推理加速：SageAttention 是量化注意力 kernel；W8A8 是权重与激活的 8-bit 量化档。与 FP8 KV（只压通信字节）是三件不同的事。
  8. Quality Drift — 长视频质量随时间的漂移度量（沿用 Rolling Forcing 论文的算法，越低越好）；流式生成最怕的就是「越播越糊」。
