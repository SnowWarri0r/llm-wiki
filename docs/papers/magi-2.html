114B 的身子，6B 的饭量

Sand.ai · 技术博客「Scaling Video Generation Models Efficiently」（2026-08-05）· 开源推理代码与权重 · Apache 2.0

输入一句话（或一句话加一张首帧图），MAGI-2 一次生成 10 秒、1080p、带同步声音的视频。它想回答的是视频生成圈一直没答清的问题：模型做大了，到底能不能稳定地换来更复杂的动作、更对的物理、更同步的音画？要做大又得用得起——一个 100B 的稠密模型每去噪一步都要动用全部参数，跑一百步谁也付不起。Sand.ai 的办法是把模型做成 114B 的"专家池"，每个 token 只调用其中约 6B，再为这种结构专门做了通信、算子和优化器，数据上则不再为了好学把复杂视频筛掉。

先记这一句每个 token 先被切成 12 个 256 维的小头，每个头在自己的 256 个窄专家里挑 6 个：每层 3,072 个专家单元、每 token 激活 72 个。这么切最大的好处在系统上——跨卡只按"头归谁"交换固定形状的数据，缓冲开训前就能分配好，路由的随机性全关在卡内。配套有融合的 MoE 算子 MagiMoE 和按"头 × 专家"分批正交化的优化器 MagiMuon。博客没有一张评测表、一条 scaling 曲线、一个消融；本页另从开源推理代码里补齐了博客没写的结构细节和参数账（总参 113.84B / 激活 5.92B，激活里路由专家只占 2.55B）。

§ 00先纠正五个容易读错的点

出处

"技术报告"就是一篇博客

没有 PDF、没有 arXiv。媒体说的"技术报告"指的就是 sand.ai 上这篇长博客。它讲架构、系统、数据三件事的思路，不含任何评测数字。有媒体提到它在 Artificial Analysis 图生视频榜排第六、10 秒 1080p 成本约 0.5 元——这些不在博客里，本页不当作论文结论用。

6B 是什么

激活 6B ≠ 挑出来的专家有 6B

按开源配置把每一块参数数一遍：激活 5.92B 里，路由专家只有 2.55B；其余 3.37B（注意力、进出投影、两种共享专家、头尾稠密层）是每个 token 都要走的固定部分。账在 § 05。

公式 vs 代码

负载偏置不在 sigmoid 里面

博客把路由写成 \sigma(Gx+b)，偏置在括号里。推理代码是先算 sigmoid 再加偏置，而且偏置只用来决定选谁；选中后的权重用不带偏置的分数归一化，再乘常数 4.9。按代码讲，见 § 06。

不是自回归

没有沿用 MAGI-1 的时间分块

一代把视频切成时间块、一块一块自回归去噪，能流式续写。二代刻意放下了这一套：先把 100B 级别的模型、系统、数据一起放大跑通，变量越少越好。MAGI-2 是整段 10 秒一起去噪，目前只支持 10 秒。

博客没写

MoE 层里还有两个常驻专家

代码里每个 MoE 层并联一个所有 token 都走的共享专家，和一个按文本 / 视频 / 音频各一份的模态专家；注意力带 attention sink 和输出门；残差是 4 路的 mHC。这些在 § 02 补齐。

现在能不能跑

8 张 Hopper、105 步、没蒸馏

权重共 307 GB（光文本编码器 Qwen3.5-27B 就 56 GB）。preview 阶段 100 步、refiner 5 步，两个 Transformer 都没做步数蒸馏；蒸馏版标着"即将发布"。

§ 01为什么要用 MoE 放大，而不是直接做大稠密模型

语言模型那边，"加参数、加数据、加算力 → 可预期地变好"已经是共识。视频这边大家也在堆。已有工作刻画过 DiT 和视频 DiT 的 loss 怎么随模型大小、数据量、学习率、batch 变化，但 loss 降了能不能稳定换成"动作更复杂、物理更对、长时更一致、音画更同步"，公开证据还很少。MAGI-2 想先把这条路搭起来，第一个问题就是：拿什么结构放大？

最直接的是稠密 Transformer——把前馈层（FFN）做宽、把层数加多。到 100B 级别它会撞上两堵墙：

训练

先撞上的是系统

参数、梯度、优化器状态和每个 token 的计算一起涨。要更狠地切分参数、做模型并行，就多出大量集合通信、跨卡同步和激活显存。视频序列又特别长，稠密放大常常还没碰到建模问题，就先成了系统问题。

推理

每一步都要全员出动

一条 10 秒视频在 MAGI-2 里是五万多个 token，生成要反复跑去噪网络上百次。100B 稠密模型每步动用全部参数，延迟和成本直接卡死实用。推理开销得在设计架构时就考虑，而不是训完再想办法。

MoE01（混合专家）的思路像医院分诊：医院养着很多科室，但每个病人只去其中几个。FFN 被拆成一大池"专家"小网络，一个路由器给每个 token 打分，只让它经过得分最高的少数几个专家。于是"模型存了多少参数"和"每个 token 花多少计算"脱钩了。博客用一组正比关系表达这件事：

F_{\text{dense}}\propto N\,P_{\text{FFN}},\qquad F_{\text{MoE}}\propto N\,P_{\text{active}},\qquad P_{\text{active}}\ll P_{\text{total}}
F_{\text{dense}},\ F_{\text{MoE}}前馈部分的主要计算量；\propto 读作"正比于"，只看量级，忽略常数。
N序列长度，即一次要处理的 token 数。视频的 N 很大，这是成本的另一个乘数。
P_{\text{FFN}}稠密模型 FFN 的参数量：每个 token 都要乘过全部这些参数。
P_{\text{active}},\ P_{\text{total}}MoE 里每个 token 实际经过的参数量、和模型存着的总参数量；\ll 读作"远小于"。

博客特意提醒了两句：MoE 不减注意力的开销；"激活参数量"也不等于端到端的计算量。它给的只是"总容量和每 token 计算解耦"这一件事。MAGI-2 把总参做到约 114B，激活约 6B：

§ 02单流骨架：文本、视频、音频排成一条序列

上一节定了"用 MoE 放大"。放大之前先定骨架——MAGI-2 沿用同门前作 daVinci-MagiHuman 的单流设计02：三种模态的 token 拼成一条序列，交给同一个 Transformer，只用自注意力，没有多塔、没有交叉注意力。

理由是三种模态描述的是同一件事：台词、口型、身体动作、环境声、音乐、镜头节奏彼此一直咬合。放在一条序列里，它们在每一层都能直接互看，而不是只在几个预先留好的接口处交换信息。对放大也更省事——后面的 MoE、并行、数据管线只需要服务一种结构。

一条 10 秒视频是多少个 token

视频preview 阶段分辨率 512×896。视频 VAE（来自 Wan2.2）空间每 16×16 像素压成一个潜变量位置：512/16=32，896/16=56，一帧 32\times56=1{,}792 个 token。
时间10 秒按 25 fps 是 250 帧；preview 配置里时间步长 8，潜变量帧数 (250-1)\,//\,8+1=32（// 是整除）。相当于先在时间上隔一帧、按 12.5 fps 生成，后面再由 refiner 加密。
合计视频 32\times1{,}792=57{,}344 个 token；音频潜变量每秒 25 个，10 秒 250 个；再加上文本编码器（Qwen3.5-27B，5,120 维特征）给的文本 token。

40 层怎么排

博客只写了"40 层、中间 36 层 MoE、边界 4 层稠密"。下面三样是从推理代码里读出来的，不影响主线，但读代码时会碰到：

头尾分模态

输入输出层各模态一套

第 0、1、38、39 层的注意力和 FFN 都按文本 / 视频 / 音频各存一份权重，token 是什么模态就走哪份。刚进来和快出去时三种数据差别最大，单独处理；中间层共享。

注意力

sink 和输出门

attention sink03是每个头一个可学习的"空位"，参与 softmax 但不贡献内容，让某个头"什么都不想看"时有地方放注意力。输出门是把注意力结果逐头乘一个 0–1 的 sigmoid 值，可以整头关小。

残差

4 路 mHC

mHC04把一条残差流扩成 4 条，每层用一个 4×4 混合矩阵在它们之间重新分配。矩阵用 Sinkhorn 迭代归一化成每行、每列和都为 1，保证信号不会越传越大或越小。

Sinkhorn 归一化就是"先让每列和为 1、再让每行和为 1"，反复做。拿 2×2 的 \begin{pmatrix}2&1\\1&1\end{pmatrix} 走一遍：列和是 3 和 2，除完得 \begin{pmatrix}0.667&0.5\\0.333&0.5\end{pmatrix}；这时行和是 1.167 和 0.833，再除得 \begin{pmatrix}0.571&0.429\\0.4&0.6\end{pmatrix}。反复 20 次（代码里的次数）收敛到 \begin{pmatrix}0.586&0.414\\0.414&0.586\end{pmatrix}，行和、列和都是 1。

§ 03把 LLM 的 MoE 直接搬过来，卡在哪

骨架定了，接下来往中间 36 层塞 MoE。最省事的是照搬 LLM 常用的 token-choice MoE05：路由器给每个 token 选 top-k 个专家，再把整个 token 的隐状态发到这些专家所在的卡上。博客认为，在视频上这样做会被通信吃掉稀疏带来的好处。

标准专家并行06里，每层 MoE 的主要通信量（忽略常数和回程）是：

C_{\text{standard MoE}}\propto N\,k\,H
C_{\text{standard MoE}}一层 MoE 跨卡要搬的数据量。
Ntoken 数。
k每个 token 激活的专家数：token 要被复制 k 份分别寄出去。
H每份寄出去的向量长度，即完整的隐藏维。

但博客强调，问题不只是"随 k 变大"，而是形状是动态的：发往哪张卡、每张卡收多少 token、接收缓冲多大，全由这一批的路由结果决定。于是有三种代价：

慢卡拖全队

straggler 与空泡

各卡的通信量和专家计算量不均，整体吞吐被最慢的那张卡卡住，其余卡等着。

峰值显存

局部 OOM

接收缓冲、重排后的激活、反向要存的张量都随本卡专家负载变化，某张卡某一步突然收太多就爆，或者分配器频繁回收缓存。

CPU 插手

主机同步

每步 token 数、路由元数据、偏移量都在变，GPU 要停下来和 CPU 对一次数，异步执行被打断。

视频把这三件事都放大了：序列比文本长得多，而且同一条序列里混着三种模态、不同噪声水平、不同空间区域和运动状态的 token，路由天然更不均匀。用 MAGI-2 的实际数字估一下：57,344 个视频 token、H=3{,}072、BF16 每数 2 字节，如果按 top-6 把整个 token 寄出去，单层单程就是 57{,}344\times6\times3{,}072\times2\approx2.11 GB，而且每步落到哪张卡都不一样。

右边就是下一节的思路。它不是让通信"消失"，而是让通信的形状和路由结果脱钩。

§ 04Multi-Head LatentMoE：每个 token 切成 12 个小头，各挑各的专家

"把 token 切成子 token、各自选专家"最早出自微软亚洲研究院的 Multi-Head MoE，但那时各个头还共用一个路由器和一个专家池。后来的 Multi-Head LatentMoE07进一步给每个头独立的路由器和独立的专家池，这才使"按头分卡"成为可能。MAGI-2 沿这条路做到了 114B。

记号：完整表示分成 M 个头，每头 H_{\text{head}} 维，H=M\,H_{\text{head}}。MAGI-2 是 M=12、H_{\text{head}}=256、H=3{,}072。一个稀疏层分三步：先切，再各头路由，最后拼回。

第一步：切

\tilde x=W_{\text{in}}\,x,\qquad \tilde x\rightarrow\bigl[x^{(1)},\dots,x^{(12)}\bigr],\qquad x^{(h)}\in\mathbb R^{256}
x进入这一层 FFN 的 token 隐状态，3,072 维。
W_{\text{in}}split 投影，一个 3,072×3,072 的矩阵：先把隐状态映射到"适合被切开路由"的坐标里，再切。
\tilde x\rightarrow[x^{(1)},\dots,x^{(12)}]把 3,072 维的 \tilde x 按顺序切成 12 段，第 h 段记作 x^{(h)}，上标 (h) 是头的编号，不是幂。
\mathbb R^{256}"256 维实数向量"。每个头只看这 256 维。

第二步：每个头在自己的 256 个专家里选 6 个

I^{(h)}=\operatorname{TopK}_6\bigl(\sigma(G^{(h)}x^{(h)})+b^{(h)}\bigr),\qquad y^{(h)}=\sum_{e\in I^{(h)}}p^{(h)}_e\,E^{(h)}_e\bigl(x^{(h)}\bigr)
G^{(h)}第 h 个头自己的路由矩阵，256×256：输入 256 维子向量，输出 256 个专家各自的打分。
\sigmasigmoid，\sigma(z)=1/(1+e^{-z})，把每个打分各自压到 0 到 1。和 softmax 不同，各专家的分数互不挤占。
b^{(h)}这个头的负载均衡偏置，每个专家一个数，只影响"选谁"，§ 06 细讲。这里按代码写在 sigmoid 之后。
\operatorname{TopK}_6取分数最高的 6 个专家，I^{(h)} 是被选中专家的编号集合。
E^{(h)}_e第 h 个头的第 e 个专家：一个 256→1,280→256 的小 FFN，激活函数是 SwiGLU7（§ 08）。
p^{(h)}_e专家 e 的权重：用不带偏置的 sigmoid 分数在选中的 6 个里归一化（除以它们的和），代码再统一乘常数 4.9。
y^{(h)}这个头的输出：6 个专家输出的加权和，仍是 256 维。

第三步：拼回去

y=W_{\text{out}}\,\operatorname{Concat}\bigl(y^{(1)},\dots,y^{(12)}\bigr)
\operatorname{Concat}把 12 个 256 维输出首尾相接，回到 3,072 维。
W_{\text{out}}merge 投影，3,072×3,072，把拼好的结果映射回 Transformer 的隐状态。

推理代码里，这一路之外还并联两条常驻支路：一个所有 token 共用的共享专家，一个按模态区分的模态专家（中间维都是 1,280），两者输出直接加到 y 上。博客没提它们。

用小数字走一遍一个头

真实是 256 个专家选 6 个，这里缩成 4 个专家选 2 个，算法完全一样：

打分路由矩阵乘出 G^{(h)}x^{(h)}=(1.2,\ 0.4,\ 0.9,\ -0.5)。
过 sigmoid\sigma(1.2)=0.769，\sigma(0.4)=0.599，\sigma(0.9)=0.711，\sigma(-0.5)=0.378。
加偏置再选偏置 b^{(h)}=(-0.2,\ +0.1,\ 0,\ 0)（专家 1 最近太忙、专家 2 太闲）。带偏置的分数 (0.569,\ 0.699,\ 0.711,\ 0.378)，前两名是专家 3 和专家 2。不加偏置的话会选专家 1 和 3。
算权重用原始分数在选中者里归一化：0.711/(0.711+0.599)=0.543，0.599/1.310=0.457，和为 1。
乘 4.9得 2.66 和 2.24。这个头的输出 y^{(h)}=2.66\,E_3(x^{(h)})+2.24\,E_2(x^{(h)})。4.9 是配置里的常数，博客没解释取值理由。

这和"3,072 个普通专家"不是一回事。每个专家单元只在一个 256 维子空间里干活，是"一大批可以独立挑选、自由组合的低维变换"，而不是一大批必须整块调用的宽 FFN。同一个 token 的不同子空间可以落到完全不同的专家组合上：每个头 256 选 6 就有 \binom{256}{6}\approx3.7\times10^{11} 种，12 个头各选各的。代价是每个专家的视野只有 256 维——和整 token 路由的宽专家比，表达力差多少，博客没有做对照。

§ 05参数账：114B 和 6B 是怎么来的

博客只给了"约 114B / 约 6B"。把开源配置里的每一块按矩阵大小数一遍，能对上，还能看出 6B 激活花在了哪里。

一个专家up 和 gate 各是 256×1,280，down 是 1,280×256：256\times1280\times2+1280\times256=983{,}040 个参数，不到一百万。
一层的路由专家12\times256\times983{,}040\approx3.02B；36 层合计 108.7B——总参的 95.5% 都在这里。
一层激活的路由专家每 token 72 个：72\times983{,}040\approx70.8M；36 层合计 2.55B。
每个 token 都要走的注意力（QKV 3,072×9,216 + 输出 3,072×3,072 + 门控，40 层）1.51B；split 和 merge 两个 3,072×3,072，36 层 0.68B；共享专家与本模态的模态专家各 11.8M/层，36 层合计 0.85B；头尾 4 层稠密 FFN（中间维 8,192）0.30B；mHC 0.02B。小计 3.37B。
对账总参 108.7+0.43+1.27+0.68+1.82+0.91+0.02=113.84B（模态专家和头尾层存三份，所以总参比激活多）；激活 2.55+3.37=5.92B。和博客的 114B / 6B 对上（没算输入输出嵌入与 adapter）。

这张账说明什么拿 MAGI-2 和"6B 稠密模型"比每 token 算力是公平的；但别把 6B 理解成"挑出来的专家有 6B"。真正被路由挑选的只有 2.55B，比固定部分还少。另一个推论：split/merge 两个方阵每层就有 18.9M，比 72 个被激活专家的 70.8M 的四分之一还多——"切头"本身也有成本。

§ 06负载均衡：给太忙的专家减分，但只在"选谁"时减

MoE 的路由器天然偏心：少数专家被挤爆、多数闲着，既浪费容量又让 § 03 说的卡间不均更严重。老办法是在损失里加一项辅助均衡损失，逼路由平均——但这项的梯度会和主任务打架。MAGI-2 用的是 DeepSeek 提出的无辅助损失做法08，每个路由头单独一套。

做法是给每个专家挂一个偏置：选专家时用"分数 + 偏置"排序，算权重时用原始分数。偏置不走反向传播，按统计到的负载直接调：

I=\operatorname{TopK}_k\bigl(s_e+b_e\bigr),\qquad p_e=\frac{s_e}{\sum_{e'\in I}s_{e'}},\qquad b_e\leftarrow b_e+\gamma\cdot\operatorname{sign}\bigl(\bar c-c_e\bigr)
s_e专家 e 的原始路由分数（MAGI-2 里就是 § 04 那个 sigmoid 输出）。
b_e专家 e 的偏置：只进排序，不进权重，也不参与梯度。
I,\ p_e选中的专家集合，和专家 e 的权重——分母只对选中的 e' 求和。
c_e,\ \bar c这一批里专家 e 实际接了多少 token，以及所有专家的平均。
\gamma,\ \operatorname{sign}每次调整的步长，和取正负号：忙了（c_e>\bar c）减 \gamma，闲了加 \gamma。

这个更新式来自 DeepSeek 的原论文；MAGI-2 只说了"每个路由头独立维护、负载统计在单独的 CUDA stream 上异步聚合"，没有公开 \gamma 和更新频率。推理代码里能看到每个头存着 expert_bias 和 expert_bias_ema 两份缓冲。

统计负载4 个专家、每 token 选 1 个、一批 8 个 token，负载 c=(5,1,1,1)，平均 \bar c=2。取示意步长 \gamma=0.1：专家 1 超载，b_1=-0.1；其余三个 +0.1。
下一批分流某 token 原始分数 s=(0.70,\ 0.62,\ 0.30,\ 0.20)，带偏置变成 (0.60,\ 0.72,\ 0.40,\ 0.30)，第一名从专家 1 换成专家 2。
权重不受偏置影响只选一个时 p_2=0.62/0.62=1；选多个时也是用 0.62 这类原始分数去归一化。
强偏好不会被硬拆如果分数是 s_1=0.95,\ s_2=0.30，带偏置后 0.85 仍大于 0.40，照选专家 1。偏置只把"选谁都差不多"的 token 分流出去。

§ 07分层头并行：IB 只搬固定形状，NVLink 负责搬专家

有了 § 04 的结构，§ 03 那个通信问题就能换一种答法。Head Parallel09：每张卡固定负责几个头，token 进 MoE 前，先按头把对应那一截维度交给负责的卡；路由、选专家、算专家都在卡内完成，算完再按头交回来。

C_{\text{Head Parallel}}\propto N\,M\,H_{\text{head}}=N\,H
C_{\text{Head Parallel}}按头分片时一层 MoE 跨卡搬的数据量。
Ntoken 数，和 § 03 同一个。
M\,H_{\text{head}}头数乘每头维度，等于完整隐藏维 H：每个 token 的每一维只搬一次，没有 k 倍的复制。

同样的 57,344 个 token：57{,}344\times3{,}072\times2\approx0.35 GB，比整 token 寄 6 份的 2.11 GB 正好少 6 倍。但博客强调更重要的是另一件事：每张卡发多少、收多少，由头的划分静态决定，缓冲开训前就能分配好。路由仍然随数据变，只是它的不规则被关进了每个头的持有者内部，不再决定跨卡通信长什么样。

一个头的 256 个专家放不进一张卡

按头分卡有个前提：负责某个头的卡得装得下这个头的全部专家。一个头 256 个专家 × 36 层，权重加梯度加优化器状态，一张卡常驻不下。MAGI-2 利用集群的两层带宽把两件事分开：

节点内用的是 ZeRO/FSDP10式的全分片：每张卡只存专家参数、梯度、优化器状态的一片，算到某层时通过 NVLink 把这层的参数临时拼全，算完再拆回去。结果是：慢的跨节点网络只跑规则的头切片，带宽高的节点内网络负责大块的专家状态搬运。

推理时的一个小浪费开源推理用 8 张卡、专家并行 8 路，但 12 个头除不尽 8。代码的处理是把头补到 16 个、每卡 2 个：0–5 号卡持有真头，6、7 号卡持有补出来的全零头，在 MoE 层照常收发但算的是零。等于 MoE 层有 2/8 的卡空转。训练时头怎么分配到节点、有没有类似浪费，博客没说。

§ 08MagiMoE：让几千个小专家跑得动

头并行把跨节点通信理顺了，但每个头的持有者在本地还得路由、重排 token、算专家。常规 MoE 运行时是按路由结果把 token 重新排序，再用 Grouped GEMM11（一次算一组大小不同的矩阵乘）跑各个专家。这对普通 MoE 够用，对 MAGI-2 不够：每层 3,072 个窄专家，每个分到的 token 少、矩阵乘的形状又小又不规则。

拿 preview 的 57,344 个视频 token 估一下：每个头里每 token 选 6 个专家，平均每个专家分到 57{,}344\times6/256=1{,}344 个 token，一次专家计算是 1{,}344\times256 乘 256\times1{,}280——对 GPU 来说是很小的矩阵乘。这种规模下，排序、kernel 启动、中间张量读写的开销会盖过矩阵乘本身，而且随头数涨。MagiMoE 因此把从路由到合并的整条路径一起优化：

融合的路由打分 + Top-K
  → 按专家紧凑排布 token
  → 融合的分组专家 FFN
  → 按路由权重合并输出

几个具体选择：路由打分用 FP32 保数值稳定，专家权重和主计算用 BF16；up 和 gate 两个投影与激活函数融合在一个 kernel 里，少写一次中间结果；长视频序列有专门省显存的前向和反向路径。

专家里的激活函数：SwiGLU7

SwiGLU12把 FFN 的升维结果分成两半：一半当"内容"，一半过 Swish 当"开关"，两半逐元素相乘。MAGI-2 用的 SwiGLU7 是 GPT-OSS 里那个变体，多了截断和一个 +1：

\operatorname{SwiGLU7}(g,\ l)=\hat g\cdot\sigma(1.702\,\hat g)\cdot(\hat l+1),\qquad \hat g=\min(g,7),\quad \hat l=\operatorname{clip}(l,-7,7)
g,\ l升维后的两半：g 是门那一半，l 是线性那一半，每半 1,280 维，逐元素计算。
\hat g,\ \hat l截断后的值：门只截上限 7，线性两头截到 ±7，防止个别大值把数值炸开。
\sigma(1.702\,\hat g)sigmoid 乘系数 1.702，\hat g\cdot\sigma(1.702\hat g) 是 GELU 的常用近似。
\hat l+1线性那一半加 1：门全开时至少把 \hat g 原样放过去。
普通值g=2,\ l=0.5：\sigma(3.404)=0.968，2\times0.968\times1.5=2.90。
门太大g=10 截成 7：7\times\sigma(11.9)\times1.5\approx10.50；不截的话是 10\times1.5=15。
门为负g=-1,\ l=0.5：-1\times\sigma(-1.702)\times1.5=-0.23，基本关掉。

负载均衡的统计（§ 06）也放在单独的 CUDA stream 上异步聚合，不和这条主计算路径抢。

§ 09MagiMuon：优化器也要知道"头 × 专家"

多头 MoE 改的不只是前向，还改了优化器看到的矩阵长什么样。稠密 Transformer 里一个权重就是一个大矩阵；MAGI-2 的专家权重天然是"头 × 专家"编号的一大批小矩阵。MAGI-2 的主力优化器是 Muon13，而 Muon 的结果恰恰取决于"矩阵怎么划分"。

Muon 对每个矩阵参数做三件事：攒动量、把动量"正交化"、按正交化后的方向更新。

R_t=\mu\,R_{t-1}+\nabla_t,\qquad O_t=\operatorname{orth}(R_t)=UV^{\top}\ \ \text{where}\ R_t=U\Sigma V^{\top},\qquad W\leftarrow W-\eta\,O_t
\nabla_t,\ R_t,\ \mu第 t 步的梯度矩阵、动量矩阵、动量系数（旧动量保留多少）。
U\Sigma V^{\top}奇异值分解：\Sigma 对角线上的奇异值是动量在各个方向上的"力度"，U,V 是方向。
\operatorname{orth},\ O_t把所有奇异值换成 1、只留方向 UV^{\top}，结果记作 O_t。实际不做 SVD，用几步 Newton–Schulz 迭代近似。
W,\ \eta被更新的权重矩阵，和学习率。

直觉：矩阵梯度常被少数方向主导，直接沿梯度走，模型只在那几个方向上猛冲。正交化把每个方向的步幅拉成一样长。比如动量 \begin{pmatrix}3&0\\0&1\end{pmatrix} 两个方向力度 3:1，正交化后变成单位阵，1:1。

为什么不能把所有专家拼成一个大矩阵

正交化作用在一整个矩阵上，同一份动量，切法不同结果就不同。用两个 1×1 的"专家矩阵"演示，动量分别是 3 和 1：

所以 MagiMuon 保留结构：路由门按头分批；专家的 up、gate、down 三个投影把"头 × 专家"展平到 batch 维，每个小矩阵独立正交化；这一大批矩阵在各 rank 之间分摊算力，而不是拼成一个人为的大矩阵。规模上每层 12\times256\times3=9{,}216 个小矩阵，36 层共 331,776 个。

不是所有参数都用 Muon：adapter、mHC、attention sink、门控相关的参数走 Adam 类更新，主体的矩阵参数用 MagiMuon。博客提到同期 Kimi K3 的 Per-Head Muon 是同一原则用在注意力上——把 Q/K/V 的动量按注意力头切开分别正交化。两者针对的结构不同，思路一样：模型有显式的头结构，优化器就该用上它。

§ 10数据：别为了好学把复杂筛掉

前面几节解决"容量怎么组织、怎么训得动"。博客的第三条腿是数据：模型只能学到训练数据里保留下来、而且被描述对了的关系。管线删掉的信息，再大的模型也补不回来。

数据过滤陷阱

早期视频模型大多在 7B 以下。小模型表达不了复杂分布，而人对画面错误又很敏感，于是社区自然形成了"以过滤为中心"的数据策略：留主体清楚、动作简单、镜头稳定的视频，删掉难学的样本。这对小模型有效，但会卡住后续放大——数据一直被修剪到小模型的能力边界，大模型看到的仍是一个被简化过的世界。博客把这叫数据过滤陷阱14：

一句话训练数据一直被简化来迁就当前模型时，数据本身就成了更强模型的能力天花板。

光少筛还不够：一段复杂视频如果只配一句通用 caption，里面的身份、动作、镜头、声音关系照样没法变成监督信号。所以新管线把标注当成数据放大的核心基建，而不是过滤后顺手补的一步。推理仓库里的提示词模板能看出标注长什么样：训练 caption 是一份结构化 JSON，global_layer 写整体语境、美学（风格、对比度、饱和度、配色、氛围）、音频基线（环境声、对白语言与说话人）、静态物体；dynamic_layer 按时间段写每段的描述、背景、光线变化和镜头运动。所以官方建议推理时先让一个 LLM 把短提示改写成这个格式。

"涌现能力"：只有定性观察

博客报告了两个现象：多镜头数据多了之后，同一个人在不同镜头里更容易保持一致；保留带字幕的数据后，出现了人物说话或唱歌时配上对应字幕特效的样本。这些不是靠专门模块加进去的。博客自己也说明这是定性观察，需要更系统的对照实验——没有给出现频率，也没有对比"筛掉 vs 保留"的受控实验。

博客把三条腿收在一起：极细粒度 MoE 提供更多条件容量，多样且标准的数据决定这些容量能不能长出有意义的分工。没有足够的数据覆盖，更大的专家池没理由分化；没有新的容量组织方式，更多数据还得被同一批稠密参数吸收。

§ 11推理管线：先低清生成，再放大精修

博客没讲推理，但开源仓库就是推理代码，配置写得很全。生成分两段：preview 在低分辨率上把整段 10 秒连声音一起去噪，refiner 再把画面放大到 1080p。

preview：去噪步怎么排

preview 用流匹配15的思路：模型预测"从当前噪声状态往干净视频走的速度"，求解器 Flow-UniPC 按一串噪声水平一步步走回去。噪声水平不是均匀排的，而是先过一次 shift16：

t'=\frac{\text{shift}\cdot t}{1+(\text{shift}-1)\,t}
t原始的噪声水平，0 是干净、1 是纯噪声，在 0 到 1 之间均匀取 100 个点。
\text{shift}偏移系数：preview 取 7，refiner 取 5。
t'实际使用的噪声水平。\text{shift}>1 时整体往高噪声那头推，步子更多花在决定构图和运动的早期。
中点t=0.5,\ \text{shift}=7：7\times0.5/(1+6\times0.5)=3.5/4=0.875。均匀排法的"一半"，实际还停在 87.5% 的噪声。
四分位t=0.25\to0.7，t=0.75\to0.955。100 步里有一半多花在 t'>0.875 的高噪声区。

每一步都要跑两遍模型：带提示词一遍、不带一遍，再用无分类器引导（CFG）17外推，视频和音频的系数分开：

v=v_{\text{uncond}}+w\,\bigl(v_{\text{cond}}-v_{\text{uncond}}\bigr)
v_{\text{cond}},\ v_{\text{uncond}}有条件、无条件两遍预测出的速度；图生视频时无条件那遍保留参考图，只去掉文本。
v,\ wv 是最终交给求解器的速度；w 是引导系数：preview 视频 5、音频 7；refiner 视频 2。

标量例：某一维 v_{\text{uncond}}=0.2,\ v_{\text{cond}}=0.5，差 0.3。视频 w=5 得 0.2+5\times0.3=1.7；音频 w=7 得 2.3；refiner w=2 得 0.8。音频推得最狠，refiner 最轻。

refiner：放大后只加一部分噪声

preview 的潜变量先用三线性插值放大：时间从 32 帧插成 2\times32-1=63 帧（相当于从 12.5 fps 回到 25 fps），空间从 32×56 放到 68×120（对应 1088×1920 像素，VAE 要求边长是 16 的倍数，所以是 1088 不是 1080）。然后不是从纯噪声重来，而是按一张 ZeroSNR 噪声表的第 220 档重新加噪：

z=\alpha\,z_{\text{up}}+\sqrt{1-\alpha^{2}}\;\epsilon,\qquad \alpha=0.839
z_{\text{up}}放大后的 preview 潜变量：已经有构图和运动，只是糊。
\epsilon标准高斯噪声。
z,\ \alphaz 是 refiner 的起点；\alpha 是信号保留系数，查表得 0.839；噪声系数 \sqrt{1-0.839^2}=0.544，两者平方和为 1，整体方差不变。

保留 84% 的信号意味着 refiner 只需要补细节，不必重画构图，所以 5 步就够。但放大后视频 token 有 63\times68\times120=514{,}080 个，是 preview 的 9 倍，全局注意力算不起——refiner 的 30 层全部用窗口注意力，每个位置只看时间和空间上邻近的块。音频在 refiner 阶段直接不参与，沿用 preview 生成的结果。

§ 12博客没有告诉我们的事

评测

零定量结果

没有 VBench、没有人类偏好、没有和任何模型的对比。"放大带来更好的生成"是全文的出发点，但没有一个数字验证它。

消融

多头 MoE 值多少，不知道

没有和整 token 路由 MoE、和稠密模型的对照；头数 12、每头 256 专家、top-6、路由缩放 4.9 怎么定的，没说。博客明确把受控消融和 scaling 曲线列为下一步。

训练配方

算力、数据量、损失都没给

训了多少 token、多少卡时、数据规模多大、视频和音频的损失怎么加权、分几个阶段、refiner 怎么训——全无。负载偏置的步长和更新频率也没公开。

系统

只有思路，没有数

头并行省了多少通信时间、MagiMoE 比通用 Grouped GEMM 快多少、MagiMuon 比 Adam 好多少、训练 MFU 多少——一个吞吐数字都没有。训练代码未开源。

数据

涌现只是定性

跨镜头身份一致、对白配字幕特效，没有频率统计，也没有"筛 vs 不筛"的对照实验。

结构

代码里的部件没解释

共享专家、模态专家、mHC、attention sink、输出门、SwiGLU7 都在代码里，博客一字未提，各自贡献也就无从得知。

§ 13定位：一份路线图，加一份能跑的权重

MAGI-2 Preview 的价值不在"生成效果多好"——那部分博客没给证据——而在两件事：把一个 100B 级视频 MoE 的架构、路由行为和推理特性完整开源出来让社区研究；以及一条明确的放大路线：容量怎么组织（极细粒度多头 MoE）、怎么训得动（头并行 + 专用算子 + 按结构分批的 Muon）、喂什么（保留复杂 + 精确标注）。

能直接拿走的

结构和系统思路

"按头切开 → 通信形状静态化"是对 MoE 系统痛点的一个干净回答，和 DeepSeek 那条"整 token 路由 + 限制路由节点"是两种解法。参数账、推理配置都能逐项核对。权重 Apache 2.0。

要留一分的

效果与归因

没有评测、没有消融，"多头 MoE 让视频模型放大得更好"目前是主张不是结论。推理也重：8 张 Hopper、105 步、没蒸馏。为了先跑通放大，还暂时放下了一代的自回归流式能力。

带走的一句一代研究"视频怎么一块块生成"，二代研究"视频模型怎么做大还用得起"：把每个 token 切成 12 个小头各选专家，让通信形状不再随路由抖动。这是一份认真的系统路线图加一份可跑的权重，不是一份能逐项复现结论的论文。

术语Glossary

  1. MoE（混合专家） · FFN 拆成一池专家小网络，路由器给每个 token 挑少数几个；总参数和每 token 计算量脱钩。
  2. 单流（single-stream） · 多种模态的 token 拼成一条序列进同一个 Transformer，只用自注意力；对立面是每模态一座塔、用交叉注意力交换信息的双流 / 多流。
  3. attention sink · 每个注意力头一个可学习的额外 logit，参与 softmax 归一化但不贡献内容，给"不想看任何 token"的头一个放注意力的地方。
  4. mHC · 流形约束的超连接：残差流扩成多路（MAGI-2 为 4 路），每层用 Sinkhorn 归一化成双随机矩阵的混合矩阵在路间重新分配信号。
  5. token-choice MoE · 每个 token 选自己的 top-k 专家（LLM 的主流做法）；对应的 expert-choice 是专家选 token。
  6. 专家并行（EP） · 不同专家放在不同卡上，token 按路由结果经 all-to-all 发过去算、再收回来。
  7. Multi-Head LatentMoE · 把 token 投影后切成多个低维头，每头独立路由器和独立专家池；MAGI-2 为 12 头 × 256 专家 × top-6。
  8. 无辅助损失负载均衡 · 每个专家一个偏置，只用于 top-k 排序、不进权重、不走梯度，按负载统计直接增减；DeepSeek 提出。
  9. Head Parallel · 每张卡固定负责若干头，跨卡只交换这些头对应的维度切片；通信 ∝ N·H、形状静态。MAGI-2 的分层版跨节点走 IB、节点内走 NVLink。
  10. ZeRO / FSDP · 把参数、梯度、优化器状态切片摊到多卡，用到某层时临时 gather 全、用完再拆回。
  11. Grouped GEMM · 一次 kernel 调用里算一组大小各异的矩阵乘，MoE 用它同时跑多个专家。
  12. SwiGLU / SwiGLU7 · 带门的 FFN 激活：一半当内容、一半过 Swish 当门再相乘；SwiGLU7 来自 GPT-OSS，门截上限 7、线性截 ±7 并加 1。
  13. Muon / MagiMuon · 对矩阵参数的动量做正交化（奇异值全拉成 1）再更新的优化器；MagiMuon 按"头 × 专家"把专家权重当一批独立小矩阵正交化并在 rank 间分摊。
  14. 数据过滤陷阱 · 为迁就当前小模型不断删掉难学的数据，使数据本身成为更大模型的能力天花板。
  15. 流匹配 · 让模型预测从噪声走向数据的速度场，生成时用 ODE 求解器（这里是 Flow-UniPC）沿速度场积分回去。
  16. timestep shift · 用 \text{shift}\cdot t/(1+(\text{shift}-1)t) 把均匀排布的噪声水平整体推向高噪声端，高分辨率、长序列常用较大的偏移系数。
  17. 无分类器引导（CFG） · 有条件、无条件各预测一次，按系数 w 沿两者之差外推，换取更贴提示词的结果。
